# Mali OpenCL 정수 내적 경로: 프로토타입 결과와 설계

- 작성: 2026-10-05 (사용자 지시: 차기 1순위, 브랜치 `perf/opencl-mali`)
- 대상: 정수 내적을 Vulkan으로는 내놓지 않고 OpenCL로는 내놓는 Mali 드라이버 (Galaxy S21 Mali-G78 r38p0, Galaxy A53 Mali-G68 r32p1)
- 코드: `adapters/llama/ggml-ameva/opencl/ameva_cl_q4k.cl`, `tests/ameva_cl_bench.c`, ameva-runtime `tools/fleet/lab/cl_bench.sh`

## 1. 무엇을 확인했는가

ggml-ameva의 검증된 수식(재배열 q4_K 디코딩, int8 활성값, 단위별 스케일)을 OpenCL C로 옮기고
`cl_arm_integer_dot_product_accumulate_int8`의 `arm_dot_acc`를 얹은 커널 세 개를 만들었습니다.

| 커널 | 역할 | Vulkan 쪽 대응 |
| :--- | :--- | :--- |
| `quant_a8` | 활성값을 단위(32개)별 int8로 | `ameva_quant_a8` |
| `gemv_q4k_i8` | 활성 1행(토큰 생성) | `ameva_mmvq`, `ameva_qmv` |
| `gemm_q4k_i8` | 활성 여러 행(프롬프트), 64×32 타일 | `ameva_mmq`, `ameva_qgemm` |

계산은 배정밀 기준과 일치합니다(같은 int8 활성값을 쓴 기준 대비 상대 오차 2e-8~8e-8, 두 기기, 모든 모양).

## 2. 실측 (2026-10-05, 한 세션에서 Vulkan과 번갈아 측정)

Vulkan 수치는 2.8.1 후보 백엔드(`7e99154`)의 f32 커널입니다. 두 기기 모두 Vulkan에 정수 내적이 없어 f32 커널이 현재의 최선입니다.
타일은 `ameva_mm_bench`의 그래프당 시간, GEMV는 Llama-3.2-1B 토큰 생성 중 디스패치당 GPU 시간입니다.
OpenCL은 이벤트 프로파일의 커널 시간(연속 실행의 중앙값)입니다.

**프롬프트 타일 (활성 352행, q4_K), ms**

| 모양 (N×K) | S21 Vulkan f32 | S21 OpenCL int8 | 배율 | A53 Vulkan f32 | A53 OpenCL int8 | 배율 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 2048×2048 | 36.9 | 16.6 | 2.2 | 56.4 | 32.7 | 1.7 |
| 8192×2048 | 122.1 | 68.3 | 1.8 | 216.6 | 130.4 | 1.7 |
| 2048×8192 | 132.9 | 71.0 | 1.9 | 222.6 | 136.5 | 1.6 |

**토큰 생성 GEMV (활성 1행, q4_K), ms**

| 모양 (N×K) | S21 Vulkan f32 | S21 OpenCL int8 | 배율 | A53 Vulkan f32 | A53 OpenCL int8 | 배율 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 8192×2048 | 1.82 | 1.21 | 1.5 | 1.81 | 1.66 | 1.1 |
| 2048×8192 | 2.08 | 1.03 | 2.0 | 2.04 | 3.08 | 0.66 |
| 2048×2048 | 0.61 | (미측정) | | 0.48 | 0.42 | 1.1 |

- S21은 측정 당시 느린 클럭 상태였습니다(Llama-3.2-1B 생성 6.7 t/s). 비교는 같은 상태에서 한 것입니다.
- 출력 투영은 실제 모델에서 q6_K·q8_0이어서 이 프로토타입(q4_K만)으로는 비교하지 않았습니다.

## 3. 측정으로 알게 된 것

1. **정렬되지 않은 로드가 가장 큰 손실이었습니다.** 바이트 포인터에 `vload16`을 쓴 첫 형태는 타일 14 GMAC/s, 16바이트 벡터 원소(`uint4`, `int4`)로 읽는 형태는 56~63 GMAC/s였습니다(S21).
2. **배리어 한 번에 여러 단위를 처리하면 더 빨라집니다.** 타일 커널은 단위(가중치 32개)마다 배리어 두 번을 지납니다. 한 번에 1 / 2 / 4 / 8 단위를 스테이징하면 S21에서 59 / 67 / 83 / 86 GMAC/s, A53에서 35 / - / 45 / 45 GMAC/s입니다. Vulkan의 `ameva_qgemm`·`ameva_mmq`에도 그대로 적용할 수 있는 결과입니다(공유 메모리 한도 안에서).
3. **GEMV는 행 하나당 작업 항목 하나가 가장 빨랐습니다.** 행 1 / 2 / 4 / 8개를 한 항목에 묶으면 S21에서 8192×2048이 1.21 / 1.15 / 1.44 / 2.0 ms, 2048×8192가 1.03 / 1.58 / 4.0 / 8.5 ms입니다. Vulkan 커널(4행 묶음, 레인 분할, 공유 메모리 축약)과 반대 방향입니다.
4. **GEMV에서는 int8과 f32의 차이가 작습니다**(같은 OpenCL 커널 구조에서 0.9~1.2배). 오전의 절제 측정(로드 30 %, 디코딩 40 %, 곱 30 %)과 같은 결론입니다. 토큰 생성의 이득은 정수 내적이 아니라 작업 분할에서 왔습니다.
5. A53의 K = 8192 GEMV는 Vulkan보다 느립니다. 긴 행을 한 항목이 순차로 처리하기 때문으로 보이며, 레인 분할이 필요합니다(미해결).

## 4. 이것이 뜻하는 것

- **프롬프트 처리**: 1B 모델 프롬프트에서 S21은 GPU 96 대 CPU 106~117 t/s, A53은 27 대 47 t/s였습니다. 타일이 1.6~2.2배 빨라지면 S21은 CPU를 넘고 A53은 CPU 수준에 닿습니다. 단, 이것은 MUL_MAT 커널만의 배율이고 그래프 전체를 OpenCL로 돌린 수치가 아닙니다.
- **토큰 생성**: S21은 1.5~2배 구간이 있어 CPU 수준에 가까워질 수 있고, A53은 지금 형태로는 이득이 없습니다. 출력 투영(로드 한계)은 그대로 남습니다.
- 아직 "Mali에서 GPU가 CPU를 넘었다"고 말할 근거는 아닙니다. 그 판정은 실모델 실행의 t/s와 KL 발산으로 합니다.

## 5. 실제 경로로 만드는 방법 (설계안)

커널 속도는 확인했으므로 남은 문제는 실행 구조입니다.

| 안 | 내용 | 장점 | 문제 |
| :--- | :--- | :--- | :--- |
| A. 혼합 | 가중치 MUL_MAT만 OpenCL, 나머지는 Vulkan | 옮길 커널이 적음 | 토큰당 MUL_MAT이 138~169개입니다. 두 API 사이를 그만큼 오가면 지금의 "그래프를 한 번에 제출" 구조가 깨지고, 버퍼 공유(`cl_arm_import_memory`)와 동기화가 필요합니다 |
| B. 전체 OpenCL | Mali에서는 그래프 전체를 OpenCL 큐로 실행 | 제출·대기 구조를 유지. API 경계 없음 | 연산 커널 전부(약 16종과 FLASH_ATTN_EXT)를 OpenCL C로 옮겨야 합니다 |
| C. Vulkan에 역수입 | OpenCL에서 찾은 구조(정렬 로드는 이미 충족, 다단위 스테이징, 행당 항목)를 Vulkan 커널에 적용 | 기존 백엔드 그대로, 5대 모두 이득 가능 | 정수 내적 자체는 S21·A53에서 여전히 못 씀 |

권고 순서:

1. **C를 먼저**: `ameva_qgemm`·`ameva_mmq`에 다단위 스테이징을 넣고 5대에서 잽니다. 변경이 작고 릴리스된 경로가 바로 빨라집니다. GEMV의 "행당 호출 하나" 레이아웃도 측정 후보(tpr 1, rows 1)에 이미 있으므로 왜 선택되지 않는지 확인합니다.
2. **B의 최소 범위**: `ac_runtime`에 OpenCL 백엔드를 두고(컨텍스트, 버퍼, 커널, 배치 제출의 같은 C ABI), 프롬프트 경로에 필요한 연산부터 옮겨 실모델 프롬프트 t/s와 KL 발산을 잽니다. 판정 기준은 Vulkan 경로와 같습니다(CPU 대비 `kld_mean <= 0.01`, `verify_kv.sh`).
3. A는 하지 않습니다(위 표의 이유).

## 6. 재현

```bash
# 기기: opencl-headers, ocl-icd(Termux), 벤더 OpenCL 드라이버
mkdir -p ~/abi-lab/cl && cp tests/ameva_cl_bench.c adapters/llama/ggml-ameva/opencl/ameva_cl_q4k.cl ~/abi-lab/cl/
AMEVA_CL_UPR=8 bash cl_bench.sh 20          # ameva-runtime tools/fleet/lab/cl_bench.sh
```

- 벤더 드라이버는 `OCL_ICD_VENDORS`로 지정합니다(스크립트가 `~/abi-lab/cl/icd/`에 항목을 만듭니다). `$PREFIX/etc/OpenCL/vendors`는 건드리지 않습니다.
- 환경 변수: `AMEVA_CL_GEMV_ROWS`(기본 1), `AMEVA_CL_LOCAL`(기본 64), `AMEVA_CL_UPR`(기본 1), `AMEVA_CL_OPTS`(추가 빌드 옵션).

## 7. 한계

- 가중치 타입은 q4_K 하나, 크기는 타일의 배수만 받습니다. 가중치와 활성값은 난수입니다.
- 측정 기기는 S21과 A53 두 대입니다. A35(Mali-G68 r38p1)는 다른 작업이 실행 중이어서 재지 못했습니다.
- 그래프 실행, 버퍼 수명, 다른 연산은 다루지 않았습니다.
