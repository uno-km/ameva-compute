# Mali OpenCL 정수 내적 경로: 프로토타입 결과와 설계

- 작성: 2026-10-05 (사용자 지시: 차기 1순위, 브랜치 `perf/opencl-mali`). 같은 날 22:40 정정(2장 머리의 정정 고지), 23:10 추가(4장: 한계 측정과 블록 정수 누적 커널. 5~8장은 그 결과로 다시 썼습니다)
- 대상: 정수 내적을 Vulkan으로는 내놓지 않고 OpenCL로는 내놓는 Mali 드라이버 (Galaxy S21 Mali-G78 r38p0, Galaxy A53 Mali-G68 r32p1)
- 코드: `adapters/llama/ggml-ameva/opencl/ameva_cl_q4k.cl`, `tests/ameva_cl_bench.c`, ameva-runtime `tools/fleet/lab/cl_bench.sh`

## 1. 무엇을 확인했는가

ggml-ameva의 검증된 수식(재배열 q4_K 디코딩, int8 활성값, 단위별 스케일)을 OpenCL C로 옮기고
`cl_arm_integer_dot_product_accumulate_int8`의 `arm_dot_acc`를 얹은 커널 세 개를 만들었습니다.

| 커널 | 역할 | Vulkan 쪽 대응 |
| :--- | :--- | :--- |
| `quant_a8` | 활성값을 단위(32개)별 int8로 | `ameva_quant_a8` |
| `gemv_q4k_i8` | 활성 1행(토큰 생성) | `ameva_mmvq`, `ameva_qmv` |
| `gemm_q4k_i8` | 활성 여러 행(프롬프트), 64×32 타일 | `ameva_mmq`, `ameva_qgemm` |
| `gemm_q4k_i8_direct` | 프롬프트, 로컬 메모리와 배리어 없이 작업 항목이 버퍼를 직접 읽는 형태(4장) | 없음 |
| `quant_a8b`, `gemm_q4k_i8_blk`, `gemv_q4k_i8_blk` | 활성 스케일을 256개 블록 단위로 두고 블록 안에서 정수로 누적(4장) | 없음(CPU 백엔드의 Q8_K와 같은 양자화) |
| `peak_dot`, `peak_fma`, `peak_load`, `peak_load_dot` | 하드웨어 한계 측정(4장) | 없음 |

계산은 배정밀 기준과 일치합니다(같은 int8 활성값을 쓴 기준 대비 상대 오차 2e-8~8e-8, 두 기기, 모든 모양).

## 2. 실측

> GEMV가 1.5~2.0배 빠르다고 적었습니다. 그 비교는 같은 조건이 아니었습니다. Vulkan 수치를 잰 시각에는 같은 Vulkan
> 커널이 평소의 두 배 시간(8192×2048 타일 122 ms, 이후 60 ms)으로 돌고 있었고, OpenCL 수치는 두 시기에 같았습니다.

> 재도 유지되었습니다.

## 3. 측정으로 알게 된 것

1. **정렬되지 않은 로드가 가장 큰 손실이었습니다.** 바이트 포인터에 `vload16`을 쓴 첫 형태는 타일 14 GMAC/s, 16바이트 벡터 원소(`uint4`, `int4`)로 읽는 형태는 56~63 GMAC/s였습니다(S21).
2. **OpenCL에서는 배리어 한 번에 여러 단위를 처리하면 빨라집니다.** 한 번에 1 / 2 / 4 / 8 단위를 스테이징하면 S21에서 59 / 67 / 83 / 86 GMAC/s, A53에서 35 / - / 45 / 45 GMAC/s입니다.
3. **같은 변경이 Vulkan에서는 역효과였습니다.** `ameva_qgemm`에 같은 구조를 넣은 튜닝 빌드(브랜치 `exp/tile-multi-unit`)는 S21에서 1단위 형태만으로 1.3배, 2단위는 2.2배 느렸습니다(8192×2048: 60.9 → 77.6~80.6 → 136~137 ms). OpenCL의 결과를 Vulkan 커널에 그대로 옮길 수 없습니다.
4. **GEMV는 행 하나당 작업 항목 하나가 가장 빨랐습니다.** 행 1 / 2 / 4 / 8개를 한 항목에 묶으면 S21에서 8192×2048이 1.21 / 1.15 / 1.44 / 2.0 ms, 2048×8192가 1.03 / 1.58 / 4.0 / 8.5 ms입니다.
5. **GEMV에서는 int8과 f32의 차이가 작습니다**(같은 OpenCL 커널 구조에서 0.9~1.2배). 오전의 절제 측정(로드 30 %, 디코딩 40 %, 곱 30 %)과 같은 결론입니다.
6. **타일 커널은 정수 내적의 산술 한계에서 멉니다.** S21, 8192×2048 타일의 절제 측정(ms, 1단위 / 8단위): 전체 100 / 68~70, 내적 제거 53 / 54, 스케일 연산 제거 99 / 74, 둘 다 제거 19 / 30. 내적 부분과 그 뒤 부동소수 연산의 조합이 시간의 대부분이고, 스테이징과 배리어만은 19~30 ms입니다. A53의 `arm_dot_acc` 산술 최대치는 264 GMAC/s인데 타일은 46 GMAC/s입니다. 커널 구조를 고칠 여지가 큽니다.
7. S21의 Vulkan 커널 시간은 시각에 따라 두 배까지 달라졌습니다(2장 정정 고지). 원인은 확인하지 못했습니다. Exynos 커널에는 `gpu_cl_boost_*`(OpenCL 작업용 클럭 부스트) 항목이 있고 S21·A53은 켜져 있지만, 측정 중 상태는 `active(0)`이었습니다.
8. **내적 내장 함수의 종류는 속도와 무관했습니다.** 표준 `dot_4x8packed_ss_int`(`cl_khr_integer_dot_product`, 빌드 옵션 `-DDOT_KHR`)와 벤더 `arm_dot_acc`를 S21에서 2회 번갈아 재면 타일 2048×2048이 16.8~18.2 대 16.8~17.7 ms, 8192×2048이 67.1~67.2 대 65.2~65.8 ms, GEMV가 1.20~1.22 / 1.03~1.04 대 1.18~1.21 / 1.02~1.03 ms입니다. A53의 드라이버(r32p1)에는 표준 내장 함수가 없어 컴파일이 실패합니다(`implicit declaration of function 'dot_4x8packed_ss_int'`). 기본값은 두 기기에서 모두 동작하는 `arm_dot_acc`로 둡니다. 내적 명령 자체를 바꾸는 것으로는 6의 격차가 줄지 않습니다.

## 4. 한계 측정과 블록 정수 누적 커널 (23:10 추가)

3장 6의 격차(타일이 내적의 산술 한계에서 멀다)가 어디에서 오는지 재고, 그 결과로 커널 형태를 바꿨습니다.

### 4.1 하드웨어 한계

작업 항목 65,536개가 다른 일 없이 한 가지만 반복하는 커널입니다(`AMEVA_CL_PEAK=1`, 항목당 2,048회, 로컬 크기 64).
1회는 가중치 단위 하나와 활성 단위 하나의 일(곱셈 누적 32개)에 해당합니다. 단위는 초당 10억 회(G회/s)입니다.

| 반복하는 일 | S21 Mali-G78 (858 MHz) | A53 Mali-G68 (897 MHz) |
| :--- | ---: | ---: |
| 레지스터 위의 내적 8개 | 32.3 (1034 GMAC/s 상당) | 10.5 (335) |
| float4 fma 8개 | 9.91 (317) | 3.18 (102) |
| 16바이트 로드 2개, 모든 항목이 같은 1 KiB 구간 | 11.46 | 3.52 |
| 로드 2개 + 내적 8개, 같은 1 KiB 구간 | 11.45 (366) | 3.58 (115) |
| 로드 2개, 항목마다 다른 1 KiB 구간(전체 64 MB) | 0.54 | 0.29 |
| 로드 2개 + 내적 8개, 항목마다 다른 구간 | 0.48 (15) | 0.26 (8.4) |

- **로드가 가장 비쌉니다.** 16바이트 로드 한 개의 처리량은 내적 한 개의 1/11~1/12입니다(S21: 내적 258 G개/s, 로드 22.9 G개/s. A53: 83.6 대 7.0).
- 로드 2개에 내적 8개를 붙여도 속도가 같습니다. 내적은 로드에 가려집니다.
- 캐시에 머물지 않는 구간의 로드는 S21에서 21배, A53에서 12배 느립니다(약 17 GB/s, 9 GB/s).
- 참고: Vulkan f32 타일(S21 86~98 GMAC/s, A53 26~27 GMAC/s)은 fma 한계의 27~31 %, 26~27 %입니다.

작업 항목 하나가 가중치 DRW행 × 활성 DRA행을 맡아 버퍼에서 직접 읽습니다. 스테이징과 배리어가 없습니다.

| direct 1×32 | 15.3~15.6 | 42.8 |

- 두 형태가 같은 수준에 모입니다(S21의 8192×2048: 타일 68.5~69.2, direct 1×88 69.7~70.8 ms). 스테이징과 배리어는 한계가 아니었습니다.
- S21, direct 1×32의 절제 측정(ms): 완전한 커널 15.3, 내적 제거 19.7, 스케일 연산 제거 17.2, 활성 단위의 d·합 로드 제거 15.3, 활성값 로드를 행마다가 아니라 단위당 한 번으로 12.6, 넷 다 제거 7.2. 내적과 부동소수 연산은 시간에 보이지 않고, 행·단위 쌍마다 하는 로드가 시간을 정합니다. 4.1과 같은 결론입니다.
- 활성값을 단위 우선(`ATRANS`: 모든 행의 같은 단위가 나란히)으로 저장해도 1×352(34.0 → 23.8 ms) 외에는 차이가 없었습니다.

### 4.3 블록 정수 누적 (`quant_a8b`, `gemm_q4k_i8_blk`, `gemv_q4k_i8_blk`)

지금까지의 커널은 행·단위 쌍(곱셈 누적 32개)마다 값 4개를 읽습니다: 활성 단위의 두 반쪽, 그 단위의 d, 합.
활성값의 스케일을 32개 단위가 아니라 256개 블록마다 하나로 두면(ggml의 Q8_K. CPU 백엔드가 q4_K 가중치에 곱하는 형식입니다) 스케일이 안쪽 루프에서 빠집니다.

```
블록마다: d_a * (d_w * sum_u(sc_u * dot(q_w, q_a)) - dmin_w * sum_u(m_u * sum(q_a)))
```

`sc_u * dot`은 블록의 8단위에 걸쳐 정수로 더합니다(최대 8 × 63 × 32 × 15 × 127 < 2^25). 쌍마다 로드 2개, 내적 8개, 정수 곱셈 누적 1개이고 부동소수 연산은 블록당 한 번입니다.

- 정합성: 같은 int8 활성값을 쓴 배정밀 기준 대비 상대 오차 2.5e-8, 모든 실행 PASS.
- 양자화하지 않은 곱과의 거리는 벤치 데이터에서 1.2e-3입니다(단위별 스케일은 6.8e-4). 이 데이터는 단위마다 크기가 0.25~6.25배로 다르게 만든 것이어서 블록 스케일에 불리합니다. 실제 모델에서의 영향은 KL 발산으로 재야 하고 아직 재지 않았습니다.

- 가장 빠른 조합이 기기마다 다릅니다(S21 1×4, A53 2×8). 같은 커널이 조합에 따라 3배 이상 차이 납니다. 가중치 4행 이상을 한 항목에 두면 두 기기 모두 느립니다.
- 원인(컴파일러의 레지스터 배치, 워크그룹의 코어 배분)은 확인하지 못했습니다. ggml-ameva가 GEMV 레이아웃을 기기에서 측정해 고르는 것과 같은 선택 단계가 필요합니다.

## 5. 이것이 뜻하는 것

- **프롬프트 타일**: 블록 정수 커널은 Vulkan f32 타일보다 S21에서 1.6~2.2배, A53에서 2.2~2.9배 빠릅니다(q4_K, 번갈아 측정). 2장의 단위 int8 타일은 S21에서 이득이 없었습니다.
- **토큰 생성 GEMV**: 블록 정수 커널은 Vulkan f32 GEMV의 디스패치당 시간보다 S21에서 1.2~2.0배, A53에서 0.9~1.8배입니다(A53의 2048×8192는 로컬 크기 64에서 0.9배, 128에서 1.2배). 이 비교는 번갈아 잰 것이 아닙니다.
- **아직 말할 수 없는 것**: "Mali에서 GPU가 CPU를 넘었다". 지금 있는 것은 q4_K 한 타입의 커널 시간입니다. 실모델에는 q6_K·q5_0·q8_0 가중치와 MUL_MAT 이외의 연산이 있고, 판정 근거는 실모델의 t/s와 KL 발산이어야 합니다. 참고로 A53의 1B 프롬프트는 GPU 27, CPU 47~48 t/s여서 그래프 전체가 1.8배 빨라져야 CPU 수준입니다.
- **설계 원칙으로 남는 것**: 이 GPU에서는 로드 수가 비용이고 내적은 거의 무료입니다. 곱셈 누적당 로드를 줄이는 형태(블록 단위 스케일, 정수 누적)가 내적 명령의 선택(3장 8)이나 배리어 줄이기(3장 2)보다 효과가 컸습니다.

## 6. 다음 단계 (설계안)

| 안 | 내용 | 판단 |
| :--- | :--- | :--- |
| A. 혼합 | 가중치 MUL_MAT만 OpenCL, 나머지는 Vulkan | 하지 않습니다. 토큰당 MUL_MAT이 138~169개이고 두 API 사이를 그만큼 오가면 "그래프를 한 번에 제출" 구조가 깨집니다 |
| B. 전체 OpenCL | Vulkan에 정수 내적이 없는 Mali에서는 그래프 전체를 OpenCL 큐로 실행(`ac_runtime`의 OpenCL 백엔드 + 연산 커널 약 16종과 FLASH_ATTN_EXT 이식) | 커널이 두 기기에서 Vulkan을 넘었으므로 프롬프트 경로의 최소 범위부터 착수합니다(아래 3) |
| C. Vulkan에 역수입 | OpenCL에서 찾은 구조를 Vulkan 커널에 적용 | 다단위 스테이징은 역효과였습니다(3장 3). 블록 정수 누적은 Vulkan에 정수 내적이 있는 기기(A35, S25, S20)의 `ameva_mmq`·`ameva_mmvq`에 적용할 수 있는 새 후보이며, 재 봐야 압니다(아래 4) |

순서:

1. **다른 가중치 타입의 블록 정수 커널**: 실모델의 MUL_MAT은 q4_K 외에 q6_K, q5_0, q8_0입니다(재배열 레이아웃은 ggml-ameva의 것을 그대로 씁니다). 타입마다 같은 벤치로 정합성과 시간을 확인합니다.
2. **기기별 선택**: 항목당 행 수와 로컬 크기를 기기에서 측정해 고르고 결과를 저장합니다(GEMV 레이아웃 선택과 같은 방식).
3. **B의 최소 범위**: S21·A53에서 프롬프트 그래프를 OpenCL로 실행해 실모델 프롬프트 t/s와 KL 발산을 잽니다. 판정 기준은 Vulkan 경로와 같습니다(CPU 대비 `kld_mean <= 0.01`, `verify_kv.sh`). 블록 단위 활성 양자화는 CPU가 쓰는 형식과 같으므로 기준 안에 들 것으로 예상하지만, 재기 전에는 결과가 아닙니다.
4. **Vulkan 정수 내적 커널에 블록 정수 누적 적용**(A35 토큰 생성 GPU 21.5 대 CPU 35~37 t/s가 대상): 튜닝 빌드로 기존 커널과 번갈아 재고, Adreno(S25·S20)에서 느려지지 않는지 함께 확인합니다.
5. 토큰 생성 경로의 OpenCL 실행은 3의 결과를 본 뒤에 정합니다.

## 7. 재현

```bash
# 기기: opencl-headers, ocl-icd(Termux), 벤더 OpenCL 드라이버
mkdir -p ~/abi-lab/cl && cp tests/ameva_cl_bench.c adapters/llama/ggml-ameva/opencl/ameva_cl_q4k.cl ~/abi-lab/cl/
AMEVA_CL_UPR=8 bash cl_bench.sh 20                         # ameva-runtime tools/fleet/lab/cl_bench.sh
bash cl_vs_vk.sh ~/abi-lab/out-rel281 3                    # Vulkan f32 타일과 번갈아 (BLK=2x8 BLKLOCAL=8,8: A53)
KIND=blk DLOCAL=8,4 GRID="1x4 1x8 2x8" bash cl_direct_grid.sh "352 2048 2048"   # 항목당 행 수
bash cl_direct_abl.sh 1x32                                 # direct 커널의 절제 측정
AMEVA_CL_PEAK=1 AMEVA_CL_PEAK_REPS=2048 ./ameva_cl_bench ameva_cl_q4k.cl 1 2048 2048 8   # 4.1의 한계
```

- 벤더 드라이버는 `OCL_ICD_VENDORS`로 지정합니다(스크립트가 `~/abi-lab/cl/icd/`에 항목을 만듭니다). `$PREFIX/etc/OpenCL/vendors`는 건드리지 않습니다.
- 환경 변수: `AMEVA_CL_GEMV_ROWS`(기본 1), `AMEVA_CL_LOCAL`(기본 64), `AMEVA_CL_UPR`(기본 1), `AMEVA_CL_ONLY`(`tile`·`direct`·`blk`), `AMEVA_CL_DRW`·`AMEVA_CL_DRA`(direct·blk의 항목당 가중치행·활성행, 기본 4·8), `AMEVA_CL_DLOCAL`(그 로컬 크기 `x,y`, 기본 드라이버 선택), `AMEVA_CL_ATRANS`(활성값 단위 우선 저장), `AMEVA_CL_PEAK`·`AMEVA_CL_PEAK_ITEMS`·`AMEVA_CL_PEAK_REPS`, `AMEVA_CL_OPTS`(추가 빌드 옵션. 절제: `-DABL_NODOT`, `-DABL_NOSCALE`, `-DABL_NOAD`, `-DABL_NOACT`. 표준 내적 내장 함수: `-DDOT_KHR`).
- Vulkan과 비교할 때는 두 커널을 같은 분 안에 번갈아 재고 실행 중 GPU 클럭을 함께 기록합니다.

## 8. 한계

- 가중치 타입은 q4_K 하나, 크기는 타일·블록의 배수만 받습니다. 가중치와 활성값은 난수입니다.
- 블록 단위 활성 양자화의 정확도는 실모델에서 재지 않았습니다(4.3).
- 가장 빠른 행 수·로컬 크기는 한 모양(352×2048×2048)에서 훑어 고른 것이고 기기마다 다릅니다. 원인은 확인하지 못했습니다.
- GEMV의 Vulkan 대비 비교는 번갈아 잰 것이 아닙니다. 출력 투영(q6_K·q8_0)은 다루지 않았습니다.
- 측정 기기는 S21과 A53 두 대입니다. A35(Mali-G68 r38p1)는 다른 작업이 실행 중이어서 재지 못했습니다.
- 그래프 실행, 버퍼 수명, 다른 연산은 다루지 않았습니다.
