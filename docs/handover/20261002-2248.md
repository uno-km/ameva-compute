## 2. 완료·검증된 작업 (A35)

### 2.1 재배열 레이아웃: `ggml-ameva-repack.h`, `ggml-ameva-repack.cpp`

**대상 타입 (12종):** q4_0, q4_1, q5_0, q5_1, q8_0, q2_K, q3_K, q4_K, q5_K, q6_K, iq4_nl, iq4_xs

**레이아웃** (텐서 하나 안에서, R행, 행당 32가중치 단위 U개, 블록 B개)

| 영역 | 내용 | 위치 |
|---|---|---|
| Q | 단위별 하위 양자화 비트. 정규 순서: 16바이트 단위에서 바이트 b = 가중치 b(하위 니블) \| 가중치 b+16(상위 니블) | 0 |
| H | 단위별 상위 비트 (q5 계열·q3_K: 4바이트, q6_K: 8바이트) | R·U·QB |
| S | 블록의 스케일 필드를 ggml과 같은 바이트 그대로 | R·U·(QB+HB) |

- 비트를 치환할 뿐이고 필드는 복사하므로 텐서 크기가 `ggml_nbytes`와 같습니다. 역양자화 값도 ggml과 같습니다.
- API
  - `ameva_repack_layout`, `ameva_repack_regions`
  - `ameva_repack`, `ameva_unrepack`
  - 행 범위판 `ameva_repack_rows`, `ameva_unrepack_rows`
- 검증: `tests/ameva_repack_check.cpp` **48/48 통과**
  - 임의 바이트 왕복
  - `ggml_quantize_chunk` 데이터 왕복
  - 역양자화 값 일치
  - 행 범위 분할 재배열·부분 복원 일치

### 2.2 QMV 커널: `shaders/ameva_qmv.comp`

**변형:** 12타입 × 2형상 = 24개
- 토큰 생성: COLS=1, ROWS=4. 활성값 8개 vec4를 레지스터에 두고 가중치 4행에 재사용합니다.
- 프롬프트: COLS=8, ROWS=1.

**바인딩과 푸시 상수**
- 바인딩 5개: Q, H, S, 활성값, 출력
- 푸시 상수 11개(44바이트)

**작업 분할**
- 64스레드 워크그룹을 행당 레인 수(tpr) 단위로 나눕니다.
  - tpr 16: U<64
  - tpr 32: U<128
  - tpr 64: 그 이상
  - 강제 지정: `AMEVA_QMV_TPR=16|32|64`
- 공유 메모리로 리덕션합니다. Adreno와 Mali는 서브그룹 크기가 달라 서브그룹 연산을 쓰지 않습니다.

**정밀도:** f16 스케일은 `ameva_h2f`(소프트웨어 변환, 서브노멀까지 정확)로 읽습니다.

**빌드:** `scripts/build_ameva_kernels.py`에 QMV 계열을 추가했습니다. 헤더 `ggml_ameva_kernels_spv.h`에는 QMM 30개, QMV 24개, 연산 커널 9개가 들어 있습니다.

### 2.3 버퍼 계층: `ggml-ameva-buffer.cpp`, 내부 헤더 `ggml-ameva-impl.h`

**재배열 여부 결정:** 텐서의 첫 쓰기 시점에 정합니다. 아래 조건을 모두 만족하면 재배열합니다.
- 버퍼 용도가 `GGML_BACKEND_BUFFER_USAGE_WEIGHTS`이거나, 시험용 설정 `AMEVA_REPACK_ALL=1`
- 뷰가 아니고 연속(contiguous)인 텐서
- 재배열 레이아웃과 QMV 커널이 있는 타입

**변환 규칙**
- 재배열된 텐서는 `tensor->extra` 표식과 버퍼별 목록으로 관리합니다.
- 이후 모든 접근이 변환을 거칩니다: set/get/memset, 뷰 경유 접근 포함.
- 첫 쓰기가 텐서 전체가 아니면, 기존 바이트를 먼저 재배열한 뒤 그 쓰기를 반영합니다(읽기-수정-쓰기). 따라서 이전 쓰기의 의미가 유지됩니다.
- `clear`의 값이 0x00 또는 0xFF가 아니면 재배열 텐서마다 그 레이아웃으로 다시 씁니다.

**non-host 전환**
- `is_host`는 `!AMEVA_REPACK`입니다. 재배열 중에는 AMEVA 버퍼가 호스트 버퍼가 아닙니다.
- 이유: 호스트 버퍼라고 보고하면 CPU 백엔드가 재배열된 바이트를 그대로 읽을 수 있습니다.
- `AMEVA_REPACK=0`이면 재배열하지 않고, 이전처럼 호스트 버퍼로 동작합니다.

**기타:** 버퍼 컨텍스트 구조체를 내부 헤더로 옮겨, 두 번역 단위에 다른 정의가 있던 ODR 위반을 없앴습니다.

### 2.4 그래프 엔진: `ggml-ameva.cpp`

**계약** (`mul_mat_reason`)
- 재배열 가중치는 QMV, 나머지는 QMM이 처리합니다. 두 경로가 받아들이는 형상은 같습니다.
- 재배열 가중치의 행 범위 뷰는 허용하고, 그 밖의 뷰는 거부합니다.
- 재배열 텐서는 MUL_MAT src0으로만 읽을 수 있고, 어떤 연산도 쓸 수 없습니다. 이를 어기는 노드는 거부합니다.

**인코더** (`enc_mul_mat`)
- 행 슬라이스마다 Q/H/S 세 범위를 바인딩합니다.
- 슬라이스는 바인딩 한계와 워크그룹 65535개를 넘지 않도록 나눕니다. 워크그룹 한계는 QMM에도 새로 적용했습니다.

**계수기** (공개 API)
- `ggml_backend_ameva_get_repacked_tensor_count`, `ggml_backend_ameva_get_repacked_bytes`
- `ggml_backend_ameva_get_qmv_mul_mat_count`
- MUL_MAT 수는 GPU 완료 후에 셉니다.

**프로파일**
- `AMEVA_PROFILE=2`의 종류명에 형상과 경로를 넣었습니다. 예: `MUL_MAT q5_0 M=1 qmv 4864x896`
- `AMEVA_PROFILE=1`에 다음 두 줄을 추가했습니다.
  - `encode_ms contract/begin/record/flush/submit`
  - `repack=... repacked_tensors=... qmv_mul_mat=...`

### 4.2 프롬프트용 타일 GEMM (재배열 가중치)

- 목적: 프롬프트 처리를 크게 줄이는 것입니다. 현재 M>1 커널은 가중치 행마다 활성값 전체를 다시 읽습니다.
  - QMM·QMV 모두 FMA 효율이 3~6%이고, L1 적재 대역폭에 묶여 있습니다.
- 설계안: 새 커널, 디코드 함수는 QMV와 공용 include로 분리합니다.
  - 워크그룹 128스레드, 타일 BN=64(가중치 행) × BM=32(토큰), K 단계 32
  - 스레드 64개가 단위 하나씩 역양자화해 공유 메모리에 f32로 씁니다.
  - 활성값 32×32 타일도 공유 메모리에 둡니다.
  - 각 스레드는 4×4 외적 누산을 합니다. 공유 메모리 약 12 KB입니다.
- 예상(계산): 활성값 트래픽이 1/16로 줄어, q5_0 4864×896 M=185가 100 ms에서 약 15~20 ms가 됩니다.
- 완료 기준
  - qmm_check 통과(M=5/8/13 포함)
  - 프롬프트 t/s가 QMM의 3배 이상
  - parity PASS
- 주의: 루프 안에 경계 분기를 두지 마십시오(§6).

### 4.3 Flash Attention 디코드 분할

- 문제: 현재 헤드당 워크그룹 1개(Qwen 0.5B는 14개)가 키 청크를 직렬로 처리합니다. 회당 239 µs, 토큰당 5.7 ms입니다.

- 목표: 토큰당 약 1 ms

### 4.4 디코드 GEMV 효율

### 환경 변수

| 변수 | 의미 |
|---|---|
| `AMEVA_REPACK=0` | 재배열을 끕니다. 버퍼는 호스트 버퍼로 동작합니다. 0과 1 외의 값은 중단합니다. |

| `AMEVA_PROFILE=1\|2` | 1: 종료 시 합계와 인코딩 분해. 2: 디스패치별 GPU 시간을 연산 종류·형상별로 집계합니다. |
| `AMEVA_TRACE=1` | 그래프별 제출·완료 기록 |

## 6. 알려진 문제와 주의사항

**측정 조건**
- A35에서 ssh로 띄운 Termux 프로세스는 Android cpuset으로 **CPU 0-2(Cortex-A55 3개)**에 묶여 있습니다(`Cpus_allowed_list: 0-2`).
  - CPU 기준선과 인코딩 시간은 이 조건의 값입니다.
  - Termux를 화면 앞에 둔 상태(top-app)와 비교할 때는 이 줄을 반드시 확인하십시오.
  - `taskset`으로 다른 코어를 지정하면 `Invalid argument`가 납니다.

**Mali 컴파일러**
- COLS=8 경로에서 단위 루프 안에 행 경계 분기를 두었더니 같은 작업이 2배 느렸습니다(190 ms 대 100 ms).
  - 분기를 루프 밖으로 옮기자 QMM과 같아졌습니다.
- 반대로 M=1 경로에서는 경계 분기를 없앤 행 고정(clamp) 방식이 더 느렸습니다(11.56 대 12.41 t/s). 그래서 원래 형태를 유지합니다.
- 커널을 바꾸면 반드시 실측으로 비교하십시오.
- Mali-G68 드라이버는 `VK_KHR_pipeline_executable_properties`를 제공하지 않습니다. 레지스터나 스필 통계를 볼 수 없습니다.

**미해명**
- 정합성 도구 실행에서는 그래프당 기록 시간이 12.5 ms(디스패치당 약 24 µs)였습니다. llama-completion에서는 34.3 ms입니다.
  - 스레드 수, polling, 컨텍스트 크기는 원인이 아님을 확인했습니다.
  - 실행 당시 cpuset이 달랐을 가능성은 확인하지 못했습니다.

**non-host 전환의 영향**
- 양자화 KV 캐시(`-ctk q8_0` 등)와 순환(recurrent) 모델 상태는 CPU가 버퍼를 직접 쓸 수 없습니다.
- llama.cpp 스케줄러는 이런 경우 "pre-allocated tensor ... cannot run the operation"으로 중단합니다.
- 해당 구성은 `AMEVA_REPACK=0`으로 실행하십시오.

**llama.cpp b8471의 GPU 버퍼 타입 순서**
- 순서는 split → 기본 → extra → CPU입니다(`make_gpu_buft_list`).
- 재배열 전용 버퍼 타입을 extra로 추가하면 가중치에는 선택되지 않습니다. 그래서 기본 버퍼 타입에서 용도로 구분합니다.

**작업 환경**
- A35 로그인 셸은 zsh입니다. 따옴표 없는 변수가 단어 분리되지 않습니다. 인자 목록은 bash 스크립트 파일로 실행하십시오.
- 로컬 셸 heredoc은 `\\`를 `\`로 축약합니다. C 문자열 이스케이프가 들어간 패치는 Write/Edit 도구로 만든 스크립트 파일로 적용하십시오.

**`ameva_mm_bench`의 시간 측정**
- 그래프 한 번의 벽시계 시간이며, 제출·대기 오버헤드(약 0.5 ms)가 포함됩니다.
- M=1의 작은 형상은 이 오버헤드와 GPU 클럭 변동이 지배합니다. 커널 시간은 `AMEVA_PROFILE=2`로 보십시오.
