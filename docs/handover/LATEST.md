## 1. 요약

- **결함을 하나 찾아 고쳤습니다(`f2265d1`).** GPU 경로에서 문맥이 가득 차 이동(context shift)하면 프로세스가 중단되었습니다.
  - 게시된 ameva-runtime 2.8.0의 백엔드(`c8aa8fd`)에 있는 결함입니다. 2.8.0에는 반영되지 않았습니다(4.1-1).
  - 검증은 Galaxy S21(Mali-G78)과 Galaxy S20(Adreno 650, Turnip) 두 대에서 했습니다. S25·A35·A53은 접속할 수 없었습니다(3장).
- **응답 텍스트를 검증 항목에 넣었습니다**(사용자 요청: 워드 샐러드, 한자·힌디어 혼입). GPU 경로에서 그런 출력은 재현되지 않았습니다(2.2절).
- **성능 실험 4건의 결과**(2.4절):
  - 프롬프트 커널의 정수 내적 에뮬레이션: 계산은 맞지만 f32 타일 커널보다 22~25배 느립니다. 채택하지 않습니다.
  - fp16 타일 커널: f32 대비 1.06~1.28배. 실험 단계이며 제품화하려면 활성값 정규화가 필요합니다.
  - GEMV 절제 측정: Mali-G78의 토큰 생성 커널은 로드 약 30 %, 디코딩 약 40 %, 곱셈 누적 약 30 %이고, 출력 투영은 로드가 75~90 %입니다.
  - 토큰 생성 전용 어텐션 경로: 계산은 맞지만 타일 커널보다 느립니다(S21 340 대 159 µs, S20 314 대 107 µs). 채택하지 않습니다.
- **결론**: 정수 내적 확장이 없는 Mali(S21·A53)에서 토큰 생성 속도가 CPU를 넘는 것은, 곱셈을 싸게 만드는 커널 작업만으로는 도달하지 못합니다. 두 실험이 같은 결과를 냈고 절제 측정이 이유를 보여 줍니다. 남은 후보는 4.2절.

## 2. 완료·검증된 작업

### 2.1 컨텍스트 이동 시 중단 (`f2265d1`)

- **증상**: `llama-completion --device AMEVA0 -c 256 -n 700 --context-shift`가 첫 이동에서 exit 134로 끝납니다. CPU 실행은 끝까지 갑니다.
  ```
  ggml-ameva: declined ROPE (cache_k_l0 (view) (view), f16): rope on non-f32 -- it runs on another backend
  ggml-backend.cpp:809: pre-allocated tensor (cache_k_l0 (view) (view)) in a buffer (AMEVA) that cannot run the operation (ROPE)
  ```
- **원인**: llama.cpp는 이동 시 저장된 키를 제자리에서 회전합니다(`llama_kv_cache::build_rope_shift`, f16 K 캐시의 뷰에 `ggml_rope_ext_inplace`). ggml-ameva는 f32 ROPE만 받았습니다. 텐서가 AMEVA 버퍼에 미리 할당되어 있어 스케줄러가 다른 백엔드로 넘기지 못하고 중단합니다. 양자화 캐시 경로(f32로 캐스트, ROPE, 되쓰기)는 이미 지원했습니다.
- **수정**: `shaders/ameva_rope.comp -DF16`(op 커널 `rope_f16`). f16 원소 단위 주소, CPU와 같은 변환(f16 → f32 정확, f32 → f16 최근접 짝수), 반 워드는 원자 연산으로 저장(NEOX는 한 워드의 두 반쪽을 다른 호출이 씁니다).
- **영향 범위**: ameva-runtime은 `--context-shift`를 넘기지 않으므로 `ameva-run exec`의 기본 실행은 해당하지 않습니다. 이동을 켜는 다른 프런트엔드가 GPU 경로를 쓰면 발생합니다.
- **검증**(S21에서 빌드한 백엔드 `c857964c2579`, 커널 헤더는 기기 생성본. S20은 같은 바이너리를 실행):

| 항목 | S21 (Mali-G78 r38p0) | S20 (Adreno 650, Turnip) |
| :--- | :--- | :--- |
| `--context-shift` 실행(프롬프트 2개, 700토큰) | 중단 없이 완료 | 중단 없이 완료 |
| 이동 후 CPU 대비 KL 발산(32위치, 기준 0.01): Qwen2.5-0.5B(NEOX) / Llama-3.2-1B(NORMAL) | 6.01e-3 / 2.76e-3 | 7.30e-3 / 2.56e-3 |
| KV 셀 제거 후 재사용(세 번째 실행 대 첫 실행) | KL 발산 0(비트 단위 동일) | KL 발산 0 |
| 2048토큰 문맥(128위치): 배치 / 토큰 단위 | 1.57e-3 / 1.62e-3, top-1 97.7 % | 1.78e-3 / 1.84e-3, top-1 99.2 % / 97.7 % |
| `test-backend-ops`: 기본 / `AMEVA_REPACK_ALL=1` | 2024/2024, 1767/1767 | 2023/2023, 1766/1766 |
| `ameva_qmm_check`, 배치 KAT | 516/516, 통과 | (S21 빌드 시 실행) |

- `test-backend-ops`의 이전 수치는 1949·1692입니다. f16 ROPE 75건이 새로 실행되어 통과합니다(다른 모드의 f16 ROPE 18건은 계속 거절).

### 2.2 응답 텍스트 검증

측정: ameva-runtime `tools/fleet/lab/text_soak.sh`, `soak_scan.py`. 2.8.0에 들어간 백엔드(`c8aa8fd`), Qwen2.5-0.5B, 채팅 템플릿, 영어·한국어 질문 6개, 응답 255토큰.

| 경로 | 응답 수 | 이질 문자가 있는 응답 | 내용 |
| :--- | ---: | ---: | :--- |
| CPU (S21·S20 같은 출력) | 18 | 2 | 한국어 응답에 한자 2자("例如"), 토큰 한도에서 잘린 문자 1건 |
| GPU, S21 (Mali-G78, f32·에뮬레이션 경로) | 18 | 0 | 없음 |

- 한자 혼입은 CPU에서도 나옵니다. 0.5B 모델의 성질입니다. 두 경로 모두 한국어 응답의 내용 품질은 낮습니다(반복, 사실 오류).
- 표본이 작습니다(기기·경로당 18개). "GPU 경로에서 발생하지 않는다"가 아니라 "이 표본에서 손상된 출력이 재현되지 않았다"입니다.
- 사용자가 본 현상의 조건(어느 앱, 어느 경로, 어느 모델)은 확인하지 못했습니다(7장 1).
- 알려진 다른 원인: 번들의 업스트림 ggml-vulkan은 플래시 어텐션을 켜면 손상된 텍스트를 냅니다(ameva-runtime `RELEASE_NOTES.md` Known issues 1). ggml-ameva 플러그인을 쓰지 않는 경로(`llama-server`, termux-llamacpp)가 해당할 수 있습니다.

### 2.3 `ameva_llm_parity` 확장

- `--batch`, `--score-step`: 긴 청크를 `llama_decode`당 256토큰으로 나누고 n번째 위치만 채점합니다.
  - 기본값으로 `--ctx 2048`을 돌리면 로짓(1,023위치 × 어휘 151,936 × 4바이트 = 0.6 GB)이 세 군데에 잡힙니다. A53(5.4 GB)에서 Termux가 종료되었습니다.
- `--kv-ops K`: 컨텍스트 이동(CPU의 같은 이동과 비교), KV 셀 제거·재사용(세 번째 실행 대 첫 실행, 기준 `kld_max <= 1e-4`).
- `--ref-kv TYPE`: 기준 실행의 KV 캐시 타입을 따로 지정합니다. 캐시 타입의 영향과 백엔드의 영향을 가릅니다.

### 2.4 성능 실험

**(1) 프롬프트 커널의 정수 내적 에뮬레이션** (`exp/int-dot-emulation-mmq`)

- `ameva_qmm_check` 516/516(정수 내적 경로 174건). 계산은 맞습니다.
- S21, 한 번의 곱(ms): f32 타일 커널 / 에뮬레이션 = 8.0 / 176, 35.7 / 901, 35.2 / 862.

- 레이어당 시간(Qwen2.5-0.5B, 키 256칸): S21 타일 159 µs / 새 경로 340 µs(22.8~23.3 → 20.9~21.1 t/s), S20 107 / 314 µs(23.8 → 20.2~21.4 t/s).
- S21의 디스패치별 시간: 점수 75 µs, 부분합 255 µs, 병합 12 µs. 확률을 열마다 다시 계산하던 첫 형태와 공유 메모리에 한 번만 두는 형태의 시간이 같았습니다.
- 타일 커널의 키 분할 크기(`AMEVA_FA_SPLIT_KEYS` 64·128·0)를 바꿔도 어텐션 합계 시간은 같았습니다.
- 해석: 한 줄 어텐션의 일은 작고(약 50만 연산, 대부분 K·V의 f16 → f32 정확 변환) 워크그룹 몇 개에서만 돕니다. 워크그룹 하나가 내는 처리량은 초당 약 2.5 G 연산으로, GPU가 가득 찼을 때보다 훨씬 낮습니다. 배리어를 없애도 대체 디스패치가 같은 제약을 받고, 디스패치 둘이 더해집니다. 일정이 아니라 키당 일을 줄여야 합니다(4.2-1).

### 2.5 q8_0 KV 캐시 (정정 포함)

- 직전 문서의 "q8_0은 CPU와 같은 출력"은 같은 캐시 타입끼리(GPU q8_0 대 CPU q8_0) 비교한 결과입니다. 캐시 타입 자체의 영향은 재지 않았습니다.
- f16 캐시의 CPU를 기준으로 재면(Qwen2.5-0.5B, 16위치) q8_0 캐시는 CPU에서 3.6e-2, GPU에서 3.0e-2~3.3e-2입니다. 기준 0.01을 넘습니다.
- 컨텍스트 이동 후(64위치)에는 CPU 0.52, GPU 0.50으로 벌어집니다. 세 실행 모두 perplexity는 약 500입니다. 캐시 타입의 성질이며 백엔드 차이가 아닙니다.
- 기본 캐시는 f16입니다. q8_0은 메모리 절감용 선택 기능이고, 이동과 함께 쓰면 f16과 다른 출력을 냅니다.

## 4. 남은 개발 과제 (전체, 우선순위 순)

### 4.1 검증 부채

1. **`f2265d1`을 나머지 기기에서 검증하고 2.8.x로 게시**: Adreno 830(S25)과 Mali-G68(A35, A53)에서 `verify_kv.sh`. S21·S20은 통과했습니다. 번들용 백엔드는 S21에서도 빌드할 수 있습니다(5장). 게시는 사용자 승인 후.
2. `550552e`(토큰 생성 에뮬레이션)의 `test-backend-ops`는 `f2265d1` 빌드로 S21과 S20에서 함께 통과했습니다.
3. A35의 Gemma-2-2B KL 발산(이월).
4. `scripts/termux/lab/tune_verify.sh`를 새 레이아웃 후보에 맞게 갱신(이월).
5. 2B 이상 모델의 속도 실측(이월).

### 4.2 성능

1. **f16 → f32 변환 비용**: 어텐션의 K·V 로드와 스케일 디코딩이 쓰는 `ameva_h2f`는 분기 포함 약 15연산입니다. `unpackHalf2x16`에 서브노멀 보정을 붙인 형태로 줄일 수 있는지 측정합니다. 어텐션은 토큰 시간의 5~12 %이고 그 일의 절반가량이 이 변환입니다. 드라이버마다 변환 결과를 `test-backend-ops`와 `ameva_qmm_check`로 확인해야 합니다. 토큰 생성 전용 어텐션 경로(2.4-5)는 시도했고 더 느렸습니다.
2. **fp16 타일 커널 제품화**: 활성값 단위별 정규화 전처리(`ameva_quant_a8`과 같은 구조)를 넣어 범위 문제를 없앱니다. S21의 1B 프롬프트(CPU 106~117, GPU 96 t/s)를 CPU 수준 이상으로 올릴 수 있습니다. A53(27 대 47)은 넘지 못합니다.
3. **확장 없는 Mali의 토큰 생성(S21·A53)**: 2.4절의 결론대로 곱셈 비용을 줄이는 방법은 효과가 없습니다. 남은 후보는 디코딩 비용 절감(정수 값에 스케일을 단위별로 적용하는 형태)과 OpenCL 경로(두 기기의 OpenCL 드라이버는 int8 내적을 제공)입니다. 둘 다 CPU를 넘는다는 근거는 없습니다.
4. **출력 투영**: 로드 한계입니다. 가중치를 덜 읽는 방법(상위 후보만 정밀 계산)은 로짓 전체를 바꾸므로 선택 기능으로만 가능합니다.
5. 이월: CPU 기록 시간(토큰당 2~10 ms), S25의 대기 시간, S21 거버너, FA 끔 경로, 융합 확대, `mali_qmv` 정리, Mali의 MMQ 타일 조정.

### 4.3 기능

1. `GET_ROWS`(임베딩 q5_0·q6_K)는 거절되어 CPU에서 실행됩니다(토큰당 1회).
2. 양자화 KV 타입 확대: 속도 이득이 없고 2.5절의 정확도 영향이 있어 낮은 우선순위입니다.
3. 런타임 쪽: `llama-server`·termux-llamacpp가 플러그인을 쓰게 하기.
4. 이월: 정확도 판정 모드, STT·디퓨전의 AMEVA 경로.

## 5. 환경과 명령

- **빌드 기기**: S25가 없을 때 S21에서 빌드합니다(clang 21, glslang 11:16.3.0, spirv-val, patchelf, 시스템 `libvulkan.so`). S20은 Termux 범용 Vulkan 로더(`libvulkan.so.1`)에 링크되어 `build_runtime_backend.sh`가 거부합니다.
- **개발 빌드**: ameva-runtime `tools/fleet/lab/dev_build.sh <tgz> <out> <tag>`. 생성된 커널 헤더(`<out>/ggml_ameva_kernels_spv.h`)를 저장소에 반영합니다.
- **KV 경로 검증**: `verify_kv.sh <out> <tag>`(이동·재사용·긴 문맥·텍스트·`test-backend-ops`). S21에서 약 25분.
- **응답 텍스트**: `text_soak.sh <out> <tag> [n]` 후 `python3 soak_scan.py ~/abi-lab/soak/<tag>`.
- **커널 단위 시간**: `mmq_bench.sh <out> [iters] [mode...]`, 토큰 생성 구성은 `prof_dec.sh <out>`.
- **절제 측정**: `abl_run.sh <tgz> <기준 out>`.
- **기기에서 파일 가져오기**: `ssh <기기> 'cat <파일>' > <로컬>`. `scp <기기>:<파일>`은 이 PC에서 멈췄습니다.

## 6. 알려진 위험과 주의사항

- **실행 모양이 새로우면 메모리를 먼저 계산합니다.** 로짓은 채점 위치 × 어휘 × 4바이트이며 컨텍스트마다, 도구의 사본마다 잡힙니다.
- **기기를 여러 세션이 함께 씁니다.** `ps`와 `free -m`을 별도 명령으로 확인하고 결과를 읽은 뒤 작업을 시작합니다. 확인과 시작을 한 명령에 넣어 다른 세션의 작업 위에 실행한 적이 있습니다(S20, 즉시 중지).
- **`pkill -f <패턴>`은 그 패턴을 담은 자신의 ssh 셸도 끝냅니다.** `pgrep -f "[l]lama-completion"` 형태로 찾고 `/proc/<pid>/environ`으로 소유를 확인합니다.
- **S21의 GPU 클럭 상태**에 따라 같은 커널이 2배 이상 차이 납니다(4864×896: 231 µs / 551 µs). 비교는 같은 상태에서 번갈아 측정합니다.
- **Mali의 셰이더 구조 민감성**: 에뮬레이션 프롬프트 커널의 22~25배 감속은 연산 수로 설명되지 않습니다(누적 변수 32개가 안쪽 루프에 살아 있음). 새 커널은 실모델 크기에서 먼저 한 번 잽니다. `ameva_qmm_check`는 작은 행렬이라 이런 감속을 보여 주지 않습니다.
- S21의 `~/abi-lab/tbo_run.sh`가 CRLF 상태였습니다(저장소의 `scripts/termux/lab/tbo_run.sh`는 LF). 기기에서 고쳤습니다. 기기 스크립트가 `set: -: invalid option`으로 실패하면 줄바꿈을 먼저 봅니다.
